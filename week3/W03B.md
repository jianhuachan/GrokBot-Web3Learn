### 补充说明

- **合约地址怎么来：** 普通部署（`CREATE`）时，新合约地址由**部署者地址**和该部署者当时的**部署 nonce** 推导得出，不需要事先「挑选」一个地址。`CREATE2` 是另一套规则，还要加入 salt 和初始化代码的哈希，和「部署者 + nonce」不是同一套算法。更完整的限定见第 5 节。
- **交易排序：** 链上以实际执行顺序为准，不承诺谁先广播、谁先点击就一定先成交。同一账户发出的交易还会受该账户 nonce 顺序约束。
- **storage 写入的 gas：** 成本是有条件的，不是一个固定数字。例如把存储从 0 改成非 0、改已有值、或清回 0，消耗（以及是否有退款）都不一样；编辑器或 Remix 上的估气只是估算。
- **`nonpayable` 不等于免 gas：** 它只表示调用时不能附带 ETH。`set` 这类要改状态的函数仍然要发交易、消耗 gas。主聊天讲解 `set` 的 ABI 时已经说明过这一点。
- **ERC-20 `transfer` 的常见 ABI 形态**（标准接口示例，不是本仓库里某个合约的原文；完整示例、参数命名和数量单位见第 5 节）：

```json
{
  "type": "function",
  "name": "transfer",
  "inputs": [
    { "name": "to", "type": "address" },
    { "name": "value", "type": "uint256" }
  ],
  "outputs": [{ "name": "", "type": "bool" }],
  "stateMutability": "nonpayable"
}
```

- **`immutable` 不是可转移所有权：** `immutable` 变量在部署时（通常在 `constructor` 里）赋值，之后不能再改。若所有权需要转移，应使用可变的状态变量，并提供更新函数（例如 `transferOwnership`），而不是把 owner 写成 `immutable` 再期望以后改掉。
- **`require(msg.sender == owner)`：** 用调用者地址和 owner 做权限检查，条件不成立就回滚。这和 W03A 里 Coin 合约 `require(msg.sender == minter)` 是同一类访问控制。

1. **`get` 和 `set` 怎么调用：** `get` 用 `eth_call` 只读，不付链上 gas；`set` 要改状态，必须发交易并消耗 gas。这与第 1.1 节已核实的判断一致，这里补上读操作走 `eth_call` 的说法。
2. **`view` 会不会耗 gas：** `view` 函数也可以通过交易来执行，那样仍然会消耗 gas。通常的用法是只读调用（不发交易），这时不付链上 gas。
3. **nonce 与 `CREATE` 地址：** 普通部署（`CREATE`）时，新合约地址由部署者地址和该账户当时的 nonce 按固定公式算出，不是只看合约代码。限定条件见第 5.1 节：所谓「相同部署顺序」只有在前序交易也相同、因而创建时 nonce 也相同的前提下，才会得到同一地址；部署交易本身也会消耗 nonce。`CREATE2` 则另用部署者、salt 和 initcode hash。
4. **`deployedContracts.ts` 给谁用：** 这个文件供 Next.js 前端定位已部署合约的地址，以及可以调用的 ABI。生成方式见第 11 条，不要把它理解成链上状态本身。
5. **ERC-20 `amount` 的类型和精度：** `transfer` 的数量参数是 `uint256`，不是 `uint8`。`uint256` 才能放下常见代币的最小单位数量；`uint8` 最大只有 255，不够用。举例：ETH 是 18 位小数，1 ETH = `10^18` wei，但要明确：**原生 ETH 不是 ERC-20**。WETH 等常用代币多为 18 位，USDC 是 6 位（1 USDC = `1000000`），具体代币要以它的 `decimals` 为准。ABI 完整示例见第 5.2 节。
6. **同时调用 `set` 的排序：** 链上会按顺序执行，后一次写入会覆盖前一次写入。不能无条件说「同时调用就没有冲突」。同一账户发出的交易还可能出现 nonce 碰撞或被替换。
7. **若要可转移的 owner：** 应使用普通 storage 里的 `owner` 变量，不要用 `immutable`；并提供只有 owner 能调用的 `transferOwnership`。这里只解释做法，不改现有合约代码。
8. **给 `set` 加访问控制：** 在 `set` 里写 `require(msg.sender == owner)`，就只有 owner 能调用。注意：合约里要先有 `owner` 变量，这个检查才有意义。
9. **以太坊主网累计部署量：** 109,335,417，截至 2026-11-14 UTC 完整日，来源 [Etherscan 合约部署统计](https://etherscan.io/chart/deployed-contracts)。这是历来累计部署量，不要当成当前仍存在或仍在使用的存量。
10. **主网谁能部署：** 以太坊主网无需许可，任何人都可以部署；前提是账户里有 ETH 用来付 gas，并且这笔交易满足网络规则。

### 5.1 nonce 与 CREATE 合约地址

普通部署（`CREATE`）时，新合约地址由一个固定公式算出：由**部署者地址**和该部署者在这次创建时的 **nonce** 共同决定，不是只看合约代码是否相同。

nonce 是一个账户已经发出的交易计数。每发出一笔交易，nonce 就会往上加；**部署合约的交易也会消耗 nonce**，和普通转账、调用一样计入这个计数。

因此，同一个部署者，如果创建时的 nonce 也相同，就会得到同一个合约地址。这里说的「相同部署顺序」只有一个前提：该账户在这笔部署之前的交易也相同，创建时的 nonce 才会相同。不能把「看起来按同样顺序部署」无条件等同于「地址一定相同」——只要前序交易不一样，nonce 就会变，地址也会变。

`CREATE2` 是另一套规则：地址由部署者、salt 和初始化代码的哈希（initcode hash）共同决定，不再只用「部署者 + nonce」。

### 5.2 ERC-20 `transfer`

完整 ABI 示例如下：

```json
{
  "type": "function",
  "name": "transfer",
  "inputs": [
    { "name": "to", "type": "address" },
    { "name": "amount", "type": "uint256" }
  ],
  "outputs": [
    { "name": "", "type": "bool" }
  ],
  "stateMutability": "nonpayable"
}
```

- `inputs` 里的名称（这里是 `to`、`amount`）只是本示例的命名，不是标准强制的字段名。第 4 节补充说明里曾用 `value` 作为第二个参数名，和这里的 `amount` 一样只是示例命名，类型仍是 `uint256`。
- 代币数量要用最小单位。USDC 是 6 位小数（decimals = 6），所以 1 USDC 写成 `1000000`。其他代币要先查它的 `decimals`，再换算。
- `nonpayable` 表示调用时不随这笔调用附带 ETH，但交易仍然需要 gas。
