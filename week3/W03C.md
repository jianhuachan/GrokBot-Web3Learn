## 1. 已核实的问答与代码（主聊天）

### 1.1 `emit` 应该写在赋值前，还是赋值后？

**提问：** 你现在的 `set` 只改 `storedData`。如果要在改值时发出事件，你觉得 `emit` 应该写在 `set` 里的哪一步：赋值前，还是赋值后？

**Kian：** 我认为是改置后

**判定：** 正确（常见写法，不是语言强制要求）。✅

**当时说明：** 放在赋值后很合适：先更新状态，再发出日志，说明这次修改的结果。不过 Solidity 并不强制这个顺序。

若事件还要记录「谁改的、旧值、新值」，就必须在赋值前先保存旧值。当时给出的写法是：

```solidity
uint oldValue = storedData;
storedData = x;
emit ValueChanged(msg.sender, oldValue, x);
```

说明：上面这小段是当时讲解用的示例，事件名写成了 `ValueChanged`。你后来实际代码里的事件名是 `ValueChange`（没有最后的 `d`），见第 1.3 节。`msg.sender` 是本次调用者的地址；如果赋值后再读取 `storedData` 当旧值，拿到的就已经是新值了。

### 1.2 「`emit` 就是 Logs 里面的内容吗？」

**Kian：** emit ValueChang就是Logs 里面的内容吗

按当时截图里「只有 `sender`、`oldValue` 带 `indexed`，`newValue` 未索引」的声明，日志会分成：

- `topics[0]`：事件签名的哈希，用来识别事件。
- `topics[1]`：`sender`（有 `indexed`），为补零到 32 字节的调用者地址。
- `topics[2]`：`oldValue`（有 `indexed`）；截图中全零，表示旧值是 `0`。
- 日志自己的 `data`：没有 `indexed` 的 `newValue`，那次调用应是 `set(1122)`，新值应出现在这里。

当时还特别提醒：截图上方的 **Data 是交易输入**（表示调用 `set(1122)`），不是事件日志自己的 `data`。那个页面只展示了日志的 topics，所以还没直接看到事件里的新值。

### 1.3 最新截图中的事件定义与 `set` 实现

这不是口头答题，而是你编写并截图的合约代码。当前工作区中未提交的 `week2/scafflod-learn/packages/hardhat/contracts/SimpleStorage.sol` 与截图一致，核心顺序正确。✅

事件定义（准确名称是 `ValueChange`，不是 `ValueChanged`）：

```solidity
event ValueChange(address indexed sender, uint indexed oldValue, uint indexed newValue);
```

`set` 中的顺序是：先保存旧值，再写入新值，最后发出事件：

```solidity
function set(uint x) public {
    uint oldValue = storedData;

    storedData = x;

    emit ValueChange(msg.sender, oldValue, x);
}
```

补充：

- 在 Solidity 里，`uint` 是 `uint256` 的别名。事件的规范签名（canonical signature）**不包含参数名，也不包含 `indexed`**，类型要写成完整的 `uint256`。因此本事件的规范签名是：

  `ValueChange(address,uint256,uint256)`

- 给参数增加或取消 `indexed`，**不会改变**这条规范签名，因而也不会改变 `topics[0]`。改变的是参数在日志里的存放位置：有 `indexed` 的进入 `topics`，没有的进入日志 `data`。
- 非匿名事件（没有 `anonymous`）最多只能有 **3 个** `indexed` 参数；`topics[0]` 固定留给事件签名哈希。你现在的三个参数全部 `indexed`，已经用满这个上限。

## 2. 如何验证 `topics[0]` 签名哈希

要核对的是完整 32 字节的 Keccak-256，而不是 4 字节选择器。

- 不要用 `cast sig` 来验证事件的 `topics[0]`：`cast sig` 通常只输出前 4 字节。对这条事件，它只会得到 `0xeeef960d`，不是日志里的完整哈希。
- 正确命令是：

  ```bash
  cast keccak 'ValueChange(address,uint256,uint256)'
  ```

  如果当前 Foundry 版本支持，也可以用 `cast sig-event`。
- 若用在线工具，必须选 **Keccak-256**，不要选 NIST **SHA3-256**。两者不是同一个哈希。

本机当时没有安装 `cast`。改用项目里已有的 `js-sha3`、`viem` 和 `ethers.id` 计算同一字符串，三者结果一致，并与截图及回执中的 `topics[0]` 相同：

`0xeeef960d7e1b1b8e1f65eb9d0d5269e3ef96c46cabde99c10d0665206646c967`

## 5. 仅知话题、未见逐字稿的参考解答

这些主题出现在本次 W03-C 的学习范围和通话收尾时的笔记要求里，但本次读不到语音逐字稿，主聊天里也没有对应的逐字回答。因此**不能记录成「你当时的回答」**，对错也无法还原。准确理解写在下面，供对照。

1. **`event` 和 `emit` 的区别：** `event` 是在合约里**声明**事件的形状（名称、参数类型、哪些带 `indexed`）。`emit` 是在函数执行时**写入一条日志**。声明本身不会产生日志；只有执行到 `emit` 才会在交易回执的 Logs 里留下记录。日志写在交易收据中，不修改合约的 storage。
2. **`indexed` 的作用：** 被 `indexed` 的参数进入 `topics`，方便按该参数筛选日志；未被索引的参数进入日志 `data`。它改变的是日志编码位置，不改变合约存储，也不改变事件规范签名 / `topics[0]`。非匿名事件最多 3 个 `indexed` 参数。
3. **为何要在 `emit` 前保存旧值：** 因为 `storedData = x` 之后，状态里已经是新值。若事件需要同时报出旧值和新值，必须在赋值前写成 `uint oldValue = storedData;`，再 `emit ValueChange(msg.sender, oldValue, x)`。主聊天第 1.1 节已核实你认为 `emit` 放在赋值后，这与常见写法一致；「为何先保存旧值」的原话本次未见。
4. **如何从日志识别这是 `ValueChange`：** 看 `topics[0]` 是否等于规范签名 `ValueChange(address,uint256,uint256)` 的 Keccak-256，也就是第 2 节的完整哈希。不要只比对前 4 字节，也不要假设改了 `indexed` 之后哈希会变。
5. **为何保存 ABI 和地址：** 见第 4 节。
